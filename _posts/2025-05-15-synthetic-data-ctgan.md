For the [Italian real estate project](/projects/italian-real-estate/), I needed a public-facing dataset that preserved the useful structures and correlations of the original scraped listings without exposing the listings themselves.

This constraint was central to the project, because I wanted to create a dashboard that showed *real* insights from the scraped data, without *actually* using the scraped data.

The obvious choice was [CTGAN](https://docs.sdv.dev/sdv/single-table-data/modeling/synthesizers/ctgansynthesizer). On paper it looked *exactly* like what I was looking for:
- purpose-built for tabular data
- widely used
- relatively easy to train
- good at reproducing distributions

If only each feature's *distribution* was relevant to this project, CTGAN would have worked flawlessly.

## The Problem Was Not Distribution Shape

My real constraint, however, was not just to generate synthetic data that looks plausible *row by row*, but actually preserve the relationships between the features that make the later model and dashboard actually meaningful.

With real estate data, this means things like the relationship between:
- location and price
- surface area and price
- neighborhood context and rent
- property type and geography

CTGAN reproduced the marginal distributions reasonably well. Prices looked like reasonable prices (there were no listing priced at 1.500€ or 10 trillion €). Surface areas looked like surface areas (there were no 2sqm or 1.000.000sqm listings). Categories appeared in roughly the right proportions.

However, several key relationships between features like the relationship between a listing's **surface** and **price** degraded *badly*.

That was a huge dealbreaker, because the downstream model relies on *exactly* those correlations. In other words, if we lost those essential correlations between features any model we build would not be essentially different from a random number generator.

## The Validation That Changed the Decision

A simple check on the data generated by CTGAN clearly showed that this was not the correct route for synthetic data generation with this dataset.

I took three of the most important features identified by the rental income model predictor (in particular, the listing's location, surface and a categorical binary feature that indicates if a listing is in Milan or not), and compared what the correlation between these three features and the listing's price (i.e., the prediction label) was in the real and synthetic data. The picture is quite grim:

| Metric | Real Data | CTGAN |
|--------|-----------|-------|
| Location ↔ Price R² | 0.62 | 0.03 |
| Surface ↔ Price R² | 0.71 | 0.69 | 
| Milan price premium | +45% | +2% |

<br>

The CTGAN can reproduce the correlation between surface and price, but *completely* misses the correlation between location and price, or the effect of the "Milan price premium". This failure is easy to understand: while the relationship between surface and price can be reasonably be assumed to be roughly linear, or at least monotonic (the larger a property is, the more it will cost on average), the relationship between location (meant as a `(latitude,lngitude)` point) and price is *definitely not* linear nor monotnonic, so it is more complicated and hard to learn for a model.

For this reason, I developed my custom KNN-based synthetic data generator, which can reproduce the *actual* correlations between features as well as in the original dataset:

| Metric | Real Data | CTGAN | Custom KNN |
|--------|-----------|-------|------------|
| Location ↔ Price R² | 0.62 | 0.03 | 0.58 |
| Surface ↔ Price R² | 0.71 | 0.69 | 0.70 |
| Milan price premium | +45% | +2% | +42% |

<br>

## The Simpler Alternative Was Better

I switched to a custom K-Nearest-Neighbors generator built around a simple idea: if the point of synthetic data is to preserve local market structure, then each synthetic listing should be built from **nearby real listings <u>in feature space</u>**.

Therefore, for each synthetic record I have:

1. picked an anchor point (i.e., one listing in the *real*, scraped data)
2. identified the 5 "closest" listings in the *real* dataset, where the "distance" was calculated using price, surface, latitude, and longitude
3. created a new, *synthetic* listing by blending all numerical features of these 5 nearest neighbors by weighted average (where the weights are *inversely* proportional to the distance used in the previous point)
4. choose categorical features for this new synthetic listing by weighted voting
5. sampled boolean features probabilistically from the same neighborhood

This extremely simple method perfectly preserved correlation *by construction* instead of hoping a generative model would infer it robustly from scratch. At the same time it created new listings which contained *synthetic* but *realistic* data.

Since I wanted to recreate a total number of listings similar to the original dataset (i.e., ~1 million), I used CUDA/TensorFlow to take advantage of GPU acceleration to make the data generation *much* faster.

## The Lesson I Learned

Developing this custom algorithm was a good reminder that cookie-cutter approaches are not *always* the way to go. We are in a time now where choosing to use one model instead of another is just as simple as changing which function from a Python library we use, without necessarily needing to know all the inner workings of a given model. While this is a *very good* thing, as it makes our life *incredibly* easier, it is also a double-edged sword: just blindingly using a model without stopping to think what is going on under the hood *will* eventually lead to situations where something's not working as we expected.

*Really* understanding what each model is doing is *essential* in order to be able to get out of such situations, for example building a custom algorithm like I did.
